Title: Add a status to each visit in the Visit API

Story: As a clinic receptionist, I want each visit to carry a status (scheduled, completed or cancelled), so that the front desk can see which visits still need to happen.

**Requires a new or changed contract from:** None

Expected behaviour:
- A visit has a `status` with exactly one of three values: `SCHEDULED`, `COMPLETED`, `CANCELLED`.
- The values are defined once, as an enum in `src/main/resources/openapi.yml` (a new schema, e.g. `VisitStatus`), and used by the visit schemas. This repo is contract-first: the DTOs and API interfaces are generated from `openapi.yml` at build time, so the YAML must be changed first and the hand-written code must match what it generates.
- `status` is returned on every visit in every response that contains visits: `GET /api/visits`, `GET /api/visits/{visitId}`, and the visits nested inside pets and owners in both API versions (e.g. `GET /api/owners/{ownerId}`, `GET /api/v2/owners`, `GET /api/v2/pets`).
- `status` is optional on create and update requests (`POST /api/visits`, `POST /api/owners/{ownerId}/pets/{petId}/visits`, `PUT /api/visits/{visitId}`):
  - when it is absent on create, the visit is saved as `SCHEDULED`;
  - when it is absent on update, the visit keeps its current status;
  - when it is any other value (e.g. `DONE`, lower-case `completed`, empty string), the API returns HTTP 400 and nothing is saved.
- The status is stored in the `visits` table in a new NOT NULL column `status` that defaults to `SCHEDULED`, so existing rows get `SCHEDULED`. Write the column definition in each database's own accepted syntax (HSQLDB needs `DEFAULT` before `NOT NULL`).

Acceptance criteria:
- AC1: `openapi.yml` defines an enum with exactly `SCHEDULED`, `COMPLETED`, `CANCELLED`, and the visit response schema includes `status` referencing it.
- AC2: `GET /api/visits/{visitId}` for an existing seeded visit returns `"status": "SCHEDULED"`.
- AC3: `POST /api/visits` without `status` returns 201 and the created visit has `"status": "SCHEDULED"`.
- AC4: `POST /api/visits` with `"status": "COMPLETED"` returns 201 and a following `GET` of that visit returns `"status": "COMPLETED"`.
- AC5: `PUT /api/visits/{visitId}` with `"status": "CANCELLED"` returns 204 and a following `GET` returns `"status": "CANCELLED"`; a `PUT` without `status` leaves the stored status unchanged.
- AC6: `POST` or `PUT` with `"status": "DONE"` returns 400 and the visit is not created or changed.
- AC7: `GET /api/owners/{ownerId}` and the `/api/v2/owners` and `/api/v2/pets` responses return `status` on every visit under each pet.
- AC8: The status is saved and read correctly with every persistence profile the existing tests cover (JDBC on H2 and HSQLDB, JPA, Spring Data JPA): the existing `ClinicService*Tests` and the visit controller tests pass, with new tests for the cases above.
- AC9: `./mvnw test` passes.
- AC10 (CL-1): `"status": null` on create or update is treated as absent: create saves `SCHEDULED`; update leaves the stored status unchanged. No 400.
- AC11 (CL-2): Only an invalid `status` value (e.g. `DONE`, `completed`, empty string) returns 400. Every other unreadable or malformed request body keeps its current response on all endpoints; this story adds no new 400 cases beyond `status`.

In scope:
- `src/main/resources/openapi.yml` (enum + visit schemas).
- `model/Visit.java` (new field, stored as the enum name), and a model enum for the status if needed.
- `mapper/VisitMapper.java` only if MapStruct cannot map the field by name.
- `repository/jdbc/` visit code (`JdbcVisitRepositoryImpl`, `JdbcVisitRowMapper`, `JdbcPetVisitExtractor`) so JDBC reads and writes the column.
- `rest/controller/v1/VisitRestControllerV1.java`, `OwnerRestControllerV1.java` (add-visit endpoint) and the v2 controllers only as far as needed for the defaulting and keep-on-update rules.
- `db/h2`, `db/hsqldb`, `db/mysql`, `db/postgres` `schema.sql` (new column). `data.sql` only where a visit insert has no column list (e.g. `db/hsqldb/data.sql`): add the column list so the rows still load and take the default. No other seed-data changes.
- Tests under `src/test/java`.

Out of scope: the Angular front end (story PC-102), security/roles, any change to pets, owners, vets or specialties beyond the nested visit `status`, Docker and Kubernetes files, the Postman tests.

Attachments: none.
